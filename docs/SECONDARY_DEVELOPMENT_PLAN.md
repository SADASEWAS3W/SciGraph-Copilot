# SciGraph Copilot 双人二次开发计划

## 1. 项目目标

SciGraph Copilot 是面向科研文献的 AI 知识分析与可视化平台。用户上传论文后，系统通过 GraphRAG 构建知识图谱，并提供文献问答、引用追踪、3D 图谱探索和 ECharts 数据分析。

本次二次开发由两人并行完成：一人负责前端与可视化，一人负责 Agent 与模型服务。目标是交付一个功能完整、分工清晰、可在 GitHub 展示，并能对应目标岗位要求的基础版 AI4Science Web 平台。

| AI 场景交互 | 对话状态、执行步骤、引用与图谱联动 | 双方 |

## 3. 当前基础与开发范围

当前代码已具备 Next.js 16、React 19、TypeScript、Three.js、React Three Fiber、`d3-force-3d`、Microsoft GraphRAG 3.1、OpenAI/Ollama 配置、文档上传与索引、SSE 流式聊天及基础图谱交互。

基础版重点补充：

- SciGraph Copilot 品牌和中文界面。
- 基础 LangGraph 问答工作流。
- 可靠的流式事件、引用和实体协议。
- ECharts 科研数据分析看板。
- AI 回答、图表与 3D 图谱联动。
- 可量化的大规模图谱渲染优化。
- 测试、文档和 GitHub 演示材料。

只完成四个核心页面：项目与文档、AI 问答、知识图谱、数据看板。暂不开发多租户、付费、复杂权限、长期记忆、人工审批、多 Agent 协商、WebGPU、百万级数据和完整数据库后台。

## 5. 协作接口与数据契约

前后端并行开发前先冻结第一版契约。类型定义放入共享目录，前端可基于固定样例开发，Agent 服务完成后再切换真实接口。

### 5.1 AI 问答 SSE 事件

| 事件 | 核心数据 | 前端行为 |
| --- | --- | --- |
| `run_started` | `runId`、查询模式 | 创建回答并显示运行状态 |
| `node_started` | 节点名称、节点序号 | 展示 LangGraph 当前步骤 |
| `token` | 文本增量 | 追加流式答案 |
| `citations` | 文档、片段、来源 ID | 渲染引用卡片 |
| `entities` | 实体 ID、名称、类型 | 联动并高亮图谱 |
| `error` | 错误码、可读信息 | 展示可恢复错误 |
| `done` | 耗时、完成状态 | 结束流式状态 |

### 5.2 索引任务事件

统一使用 `queued`、`running`、`cancelling`、`cancelled`、`failed`、`completed` 状态，并携带阶段名、进度、日志时间和错误信息。进度表示工作流阶段，不承诺等同于实际剩余时间。

### 5.3 可视化数据

Agent 侧提供或转换实体、关系、社区、文档、文本单元和社区报告。所有对象使用稳定 ID；引用、AI 回答、ECharts 和 3D 图谱使用同一实体 ID 实现联动。

## 6. 技术架构

```text
前端负责人
React / Next.js / TypeScript
├─ 项目与文档管理
├─ AI 对话与 Agent 状态
├─ ECharts 数据看板
└─ Three.js 3D 知识图谱
             │ API / SSE / Shared Contracts
             ▼
Agent 负责人
Next.js Server + 基础 LangGraph
├─ 问题校验
├─ GraphRAG 检索
├─ 引用和实体整理
└─ 流式事件输出
             │
             ▼
Microsoft GraphRAG / OpenAI / Ollama
```

LangGraph 负责编排问答步骤，GraphRAG 负责索引和知识检索，Next.js API 负责调用、取消和事件转发。基础版不将简单函数强行包装为多个 Agent。

## 7. 阶段计划与双人分工

两人并行开发预计 4～6 周。每阶段以可联调的纵向功能为单位，不分别建设两套孤立模块。

### 阶段 1：项目整理与契约确定（3～5 天）

目标：建立稳定基线，让双方可以独立开发并通过样例数据联调。

| 前端负责人 | Agent 负责人 |
| --- | --- |
| 完成品牌、中文菜单和基础页面结构 | 核对 GraphRAG、OpenAI、Ollama 运行配置 |
| 整理加载、空状态和错误提示组件 | 整理索引、查询、停止任务的服务端链路 |
| 根据共享类型制作对话和图谱 Mock 数据 | 定义问答与索引 SSE 事件、错误码和返回类型 |
| 确认前端环境变量和模型配置表单 | 补充安全的环境变量样例及模型校验 |

共同交付：第一版共享契约、可启动的开发基线、README 启动说明和职责边界。

阶段验收：页面可启动；Mock 问答能播放完整事件；模型配置错误能返回明确原因。

### 阶段 2：LangGraph 流式问答与引用联动（1 周）

目标：完成可解释、可停止、有引用的文献问答主流程。

| 前端负责人 | Agent 负责人 |
| --- | --- |
| 开发对话消息、输入框和查询模式选择 | 实现“校验问题→GraphRAG 检索→整理结果→返回答案”工作流 |
| 消费 SSE 并显示 Token、节点步骤和耗时 | 输出约定的节点、Token、引用和实体事件 |
| 实现停止生成、重试、错误和无结果状态 | 实现 Abort、超时、模型异常和检索异常处理 |
| 开发引用卡片及实体点击交互 | 将 GraphRAG 结果规范化为引用和实体结构 |

共同交付：一条真实端到端问答链路，以及 local、global、drift 查询模式。

阶段验收：回答可流式展示并停止；至少显示来源或证据片段；点击实体或引用可触发图谱定位；节点执行顺序可见。

### 阶段 3：ECharts 科研数据看板（1 周）

目标：补齐复杂图表展示和多视图数据联动能力。

| 前端负责人 | Agent 负责人 |
| --- | --- |
| 封装可 resize、销毁、加载和空状态的 ECharts 组件 | 提供实体、关系、社区、文档的聚合数据接口或转换函数 |
| 实现类型柱状图、社区矩形树图、关系桑基图 | 确保聚合数据 ID 与 GraphRAG 输出一致 |
| 实现主题趋势图和实体强度热力图 | 处理缺失字段、空结果和异常结果 |
| 增加 tooltip、legend、dataZoom、图片导出 | 为联调准备小、中、大三组固定数据样例 |
| 实现图表点击与图谱筛选联动 | 配合验证统计口径和结果正确性 |

共同交付：至少五类真实数据图表，至少两张图表与 3D 图谱双向联动。

阶段验收：图表响应容器变化；事件和实例正确释放；大数据时启用 Canvas、sampling、progressive 或 large 模式。

### 阶段 4：3D 图谱交互与性能优化（1～2 周）

目标：强化 WebGL 复杂图谱能力，并形成可复现的性能数据。

| 前端负责人 | Agent 负责人 |
| --- | --- |
| 增加类型、社区、关系权重筛选 | 输出适合渲染的轻量图谱数据和必要索引 |
| 完成搜索定位、邻居高亮和关系路径展示 | 提供实体邻居、路径及社区详情查询能力 |
| 将数据转换或布局计算移入 Web Worker | 避免接口返回重复、无效或悬空关系数据 |
| 实现分批挂载、标签降级和对象复用 | 协助生成 1k、5k、10k 标准测试数据 |
| 记录加载时间、布局耗时、FPS 和内存 | 记录图谱接口响应时间和数据体积 |

共同交付：AI 回答、ECharts 与 3D 图谱共享实体状态，以及一份有环境说明的性能报告。

基础目标：1,000 节点流畅交互；5,000 节点无长时间卡死；10,000 节点可加载并通过筛选控制规模；点击反馈尽量在 200ms 内。所有数字以实测为准，未达到时如实记录。

### 阶段 5：AI4Science 演示场景（3～5 天）

目标：形成招聘方可直接理解的科研业务闭环。

| 前端负责人 | Agent 负责人 |
| --- | --- |
| 制作文献、实体、引用和统计的演示页面状态 | 选定公开科研主题并整理可合法使用的资料 |
| 优化从回答到图谱、再到看板的操作路径 | 定义 Paper、Drug、Disease、Target、Experiment 等实体 |
| 增加演示引导、示例问题和结果说明 | 调整 GraphRAG 提示词并验证实体抽取效果 |
| 准备页面截图和交互录屏素材 | 准备三个稳定的演示问题及预期证据 |

共同交付：“上传资料→构建图谱→AI 提问→查看引用→定位图谱→看板分析”的完整演示。

阶段验收：演示数据可重复构建；三个问题能得到有引用的回答；README 标注数据来源。

### 阶段 6：收尾、测试与 GitHub 作品化（3～5 天）

目标：一次性完成全项目验证和作品交付。

| 前端负责人 | Agent 负责人 |
| --- | --- |
| 补充组件、数据转换和核心 E2E 测试 | 补充 Agent 节点、GraphRAG 解析和 API 测试 |
| 检查首屏、重复渲染、资源释放和动态加载 | 检查取消、超时、并发、失败恢复和日志脱敏 |
| 整理功能截图、性能报告和前端技术说明 | 整理 Agent 架构、模型配置和数据处理说明 |
| 负责演示视频的页面操作部分 | 负责演示视频的 AI 工作流讲解部分 |

共同交付：README、架构图、性能报告、测试结果、2～3 分钟演示视频或 GIF。

阶段验收：新用户可按 README 启动；上游功能和二次开发内容区分清楚；核心流程通过；GitHub 首页能快速说明项目价值。

## 8. 协作与 Git 规则

- `main` 保存稳定发布版本，`develop` 作为日常集成分支。
- 前端使用 `feature/frontend-*`，Agent 使用 `feature/agent-*`，跨方向联调使用 `feature/integration-*`。
- 每个分支只处理一个清晰目标，通过 Pull Request 合入 `develop`。
- 共享契约先合并，再由双方分别实现；契约变更必须通知并评审另一方。
- 避免双方同时修改同一大型页面；确需共同修改时，先拆分组件或约定提交顺序。
- 提交信息使用 Conventional Commits，例如 `feat(frontend): add analytics dashboard`、`feat(agent): add graphrag workflow`。
- 每阶段进行一次功能演示和接口联调，问题记录到 GitHub Issues，不在阶段中反复执行完整测试套件。

## 9. 测试与验收策略

遵循项目 Agent Harness 规则：分阶段开发时不要求每阶段运行完整测试，仅在整个双人开发任务全部完成后执行一次完整质量门禁。

开发过程中允许必要的局部诊断，例如检查单个接口、查看浏览器错误或运行与当前修改直接相关的小范围测试，但它们不替代最终验收。

最终统一执行：

```powershell
pnpm harness:quality
```

随后双方共同人工验收：

- 文档上传、索引启动、停止和失败提示。
- LangGraph 流式问答、引用、实体和取消请求。
- ECharts 五类图表、导出和图谱联动。
- 3D 图谱搜索、筛选、高亮、路径和大数据表现。
- OpenAI 与 Ollama 配置错误时的可理解反馈。
- 完整 AI4Science 演示流程。

## 10. 工作量与交接检查

每个阶段结束时，双方只需完成以下交接：

1. 更新共享类型，或明确说明本阶段无契约变化。
2. 提供可供另一方联调的真实接口或固定 Mock。
3. 在 Pull Request 中说明功能、风险和人工验证方式。
4. 将遗留问题登记为 Issue，并标注前端、Agent 或共同负责。

若一方提前完成阶段任务，应优先协助接口联调、代码评审和文档补充，不临时扩展基础版范围。
